# Git の運用

## ブランチと区間

区間計画書（`Assets/Docs/InGame/Sections/`）1 つにつきブランチを 1 つ切り、1 区間を複数のコミットに分ける。区切りごとに、変更したファイルと確認の結果を報告して止まる。

## ローカル

commit と push はユーザーが行う。Claude は作業と検証まで済ませたら止めて、変更ファイルの一覧とコミットできる状態かを報告し、コミットの分け方とメッセージを提案する。`git commit` と `git push` は、ユーザーがはっきり頼んだときだけ実行する。

## クラウドセッション

環境変数 `CLAUDE_CODE_REMOTE` が `true` のとき。

- 作業結果を push しないと持ち出せないので、`claude/` で始まる作業ブランチへの commit と push だけを Claude が行ってよい。`main` や `feature/` のブランチには push しない。PR の作成とマージは頼まれたときだけ
- PR は、対応する `feature/` ブランチ（`claude/alpha/enemybody` なら `feature/alpha/enemybody`）にだけ出す。`main` などの統括ブランチには出さない。クラウドでは Unity を動かせず、確認の精度が落ちるため。コードだけのわずかな変更・修正、特に hotfix はこの限りではない

## コミットメッセージ

```
[prefix]本文

・補足
```

- 1行目は `[prefix]本文` の形にする。プレフィックスと本文の間にスペースは入れない
- 補足は任意。変更が多いときは、1行空けてから `・` で始まる行で書くことを推奨する
- 補足なしで済む大きさのコミットが理想。補足が要るときも 2〜3 行に収まるように、コミットを分けることを推奨する
- 種類の違う変更が混ざるときは、主な変更のプレフィックスを付ける

| prefix | 使うとき |
|---|---|
| add | ファイル・フォルダ・クラスなどの追加 |
| update | 既存クラスの更新、機能の追加・変更 |
| fix | 不具合の修正 |
| hotfix | 緊急性の高い不具合の修正。基本は `hotfix/` ブランチで使う |
| nitpick | 誤字・コメント・書式など、ごく軽微な修正 |
| clean | ファイルの削除やフォルダの整理など、プロジェクトの整備 |
