区間の番号は識別用。区間8R は 2026-10-08 に追加した区間で、区間8のあと、区間9の前に行う。

## 目的

区間0〜8で積み上がったコードを、挙動を変えずに整える。前半でソースコードの構造・命名・メンバー順を整え、後半でコメントとサマリーを整える。
区間9で敵の仕組み（`EnemySpawnAdapter` など）に種類と攻撃を足す前に、土台を読みやすくしておく。

## 前提

- 前半はスキル `code-refactoring`、後半はスキル `comment-refactoring` の進め方と基準に従う。順番は、ソースコードの整備 → コメントの整備（2026-10-08、ユーザーが決定）。コメントは構造と名前が決まってから直す方が、同じ箇所を二度直さずに済む為
- 今の仕様に対する整理だけを行う。区間9で要る変更（敵の種類ごとの体のプールなど）は先取りしない（planning-criteria の基準1）
- 挙動は変えない。挙動が変わる直し（見た目の問題など）は、この区間では扱わず「見つけた問題」に書く
- 両スキルの kizami 用の対象範囲（各スキルの `references/projects.md`）に従う

## 作業一覧

コミットは両スキルの順番に従う。前半はスキル `code-refactoring` の「コミットの順番」で、後半は層ごとの区切りで分ける。各コミットで、作業 → 検証 → 変更ファイルと確認結果の報告をして止まる。

| # | 作業 | 内容 |
|---|---|---|
| R-1 | 調べる | 対象のコードを層・機能ごとに全部読み、Notion の仕様リストとシステムリストに照らし合わせる。パッケージの API は実物で確かめる。読むだけで何も変えない |
| R-2 | 提案する | 確認項目 1〜7 ごとに、直すものと残すもの（残す理由）を出し、「決めてほしいこと」を分けて書く。ユーザーの回答で案を直し、GO をもらう |
| R-3 | ソースコードの整備 | 既知の問題 → 構造の整理（統合・削除・既存機能への置き換え） → API の形 → 大きめの作り直し → 命名 → メンバー順、の順にコミットを分ける。どのコミットを作るかは R-2 の結果で決める |
| R-4 | コメントの整備 | 区切り：Shader → BlackBoard と External → Application → Initialization → EngineAdapter（CoreSystem・Input・Player・Stage） → EngineAdapter（Enemy） → EngineAdapter（Voxel）。区切りごとに差分がコメントだけかを確かめる |
| R-5 | ドキュメントを合わせる | 全体計画書の「手本にする既存コード」「現状」「使う既存機能」と、`Assets/Docs/Voxel/` の行リンクを今のコードに合わせる。区間計画書は記録なので直さない。区間9以降の計画書の、名前や場所が変わった記述は直す |

- VR とスマホの既存コード（`Vr〜` の Adapter、`TouchLookInputSource`、ビルドモード）は、どのシーンにも置かれていないものを含めて壊さずに保つ。使われていないように見えても、2 つ目の利用者（スマホ・VR）が来る予定のものは消さない（code-refactoring の確認項目 1）
- プレイモードで確かめられるのは PC だけ。スマホと VR の経路は、コンパイルが通ることまでを確かめ、未確認として報告する
