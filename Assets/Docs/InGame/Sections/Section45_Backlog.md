## 作業者向けの前提

この計画書と子の区間の計画書だけを受け取った作業者（別の会話の AI を含む）が迷わないように書く。

### 最初に読むもの

1. リポジトリの `CLAUDE.md`（進め方、構成、どこに何があるか）
2. 着手する子の区間の計画書
3. スキル：state-centrism-architecture（層の役割と参照ルール）、usefultoolkit（BlackBoard・Initializer の書き方）、comment-refactoring（コメントの書き方）、overall-section-plan（区間の進め方）、planning-criteria（計画を出す前の基準）
4. `.claude/rules/` の C# の規約とコンパイルの手順（C# を触ると自動で読み込まれる）

### 守ること

- 着手したら、まず計画書の「既存コードの確認結果」と今のコードを突き合わせる。食い違い（行がずれた、既に直っている、前提の型がない）は、作業の前に報告して計画書を直す
- 「仮定（未確認）」と書いた原因の見立ては、確かめてから直す。確かめた結果が見立てと違えば、直す前に報告して止まる
- 「詳細仕様で決めること」は、その項目を使うコミットの前にユーザーに聞く。案のまま進めてよいかも聞く。答えはその場で計画書の表に書き込む
- コミットの単位で実装し、区切りごとに、変更したファイルと確認の結果を報告して止まる。子の区間をまたいで先走らない。ほかの区間の作業に手を付けたくなったら、計画書の「見つけた問題」に書く
- コミット・プッシュ・ブランチの作成はユーザーが行う。Claude はコミットの分け方とメッセージの案を出す（規約は `.claude/docs/GitWorkflow.md`）
- C# を直したら、`.claude/rules/unity-compile.md` の手順でコンパイルし、DLL の更新時刻まで確かめる。プレイモード中ならコンパイルの前に止めてよい
- 完了条件は、プレイモードで実際に動かして確かめる（uloop のスキル。キー入力は `uloop-simulate-keyboard`、見た目は `uloop-screenshot`・`uloop-record-video`）。動かして確かめられなかった条件は、そう書いて、どこで確かめるかをユーザーと決める
- シーンとプレハブの値は uloop の `execute-dynamic-code` で変えて保存する。アセットを足したら `uloop-verify-project` で .meta を確かめる
- 新しい型を作るときは、計画書の「新しく作る型と、今の区間で使う利用者」の表に沿う。表にない型を足したくなったら、理由を添えて先に聞く
- SerializeField の名前を変えるときは `FormerlySerializedAs` を付けて保存し直す
- 子の区間を終えたら、その計画書に「実装結果」（決めたこと・作った主なもの・完了条件の確認結果・持ち越すこと）を書き、状態を「完了（日付）」にし、全体計画書の区間一覧を更新する
