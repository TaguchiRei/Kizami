敵のスポーンを「スポーン位置 1 つにつき 1 グループ」にし、減ったグループを撤退させて補充する形に作り直す。あわせて、グループ（部隊）の意思決定を EngineAdapter の Job から Application へ移す。

この文書では、グループと部隊は同じものを指す。

## 今の実装（区間4D・9）との違い

| 項目 | 今の実装 | 改変後 |
|---|---|---|
| スポーン位置と区画 | スポーン位置は区画と関係なく、全体を 1 つのリストで順に回す | スポーン位置ごとに、属する区画を自分で指定する |
| 初期生成 | 初期生成の範囲（`EnemyInitialSpawnArea`）から、決まった数をグループの人数ずつ、範囲の中のランダムな中心に置く | 初期生成の範囲はなくす。スポーン位置ごとに、編成の 1 グループを出す |
| 実行中の生成 | 生成情報（`EnemySpawnInfo`）ごとに、間隔（既定 3 秒）でスポーン位置を回して新しいグループを出す | 間隔での生成はなくす。減ったグループの補充と、全滅したあとの出し直しだけ |
| 編成 | 初期生成の範囲と生成情報ごとに、`EnemyKind` の配列で持つ | スポーン位置ごとに、ScriptableObject の編成を指定する |
| 合流 | 4 体以下に減ったグループは、40m 以内で空きのあるほかのグループへ合流する（`EnemyGroups.TryMerge`） | なくす |
| 減ったグループ | 減ったまま戦い続ける | 一定の割合を失ったら撤退し、持ち場で補充を受けて満員に戻る |
| 部隊の意思決定 | 待機・追跡・帰還の切り替えと、外側の螺旋の目標位置の割り当てを `EnemyGroupJob`（EngineAdapter）が行う | Application が部隊ごとに決め、State で公開する。EngineAdapter は経路探索と隊列の制御を行う |

## 決めたこと

### スポーンと補充

1. スポーン位置 1 つにつき 1 グループ。グループの持ち場は、そのスポーン位置
2. スポーン位置ごとに、属する区画を自分で指定できるようにする
3. スポーン位置ごとに、出すグループの編成を指定する。編成は ScriptableObject で持つ
4. 初期生成の範囲はなくし、開始時に、スポーン位置ごとにその編成の 1 グループを出す
5. 間隔での生成はやめる。敵は補充と全滅後の出し直しでだけ出す
6. 移動中のグループが、満員の人数の一定の割合を失ったら撤退する。割合は敵の全体の設定に持ち、既定は 60%（残りが 40% 以下になったら撤退）
7. 撤退するグループは、プレイヤーを中心にしたアルキメデス螺旋で占めていた目標位置を手放し、持ち場へ帰る
8. 撤退したグループが持ち場へ帰り終えたら、減った分を持ち場に出し、合流させて満員に戻す
9. グループが全滅したら、スポーン位置ごとの間隔のあとに、満員のグループを出し直す。間隔はスポーン位置ごとに設定する
10. 補充と出し直しの回数に上限はない。スポーン位置が壊されたら、そこからは出なくなる。スポーン位置はボクセルで作る
11. 帰還の途中で進めなくなったら、その位置を臨時の拠点（持ち場）にする（区間4D の 2a のまま）。臨時の拠点にいる間は補充しない。全滅するまで、そこを拠点にする
12. ほかのグループとの合流はなくす。区間4C の計画で入ったが、仕様として必要なものではなかった
17. グループごとの交互の前進とレーンの待ちは入れない。区間4D で、入れても切っても重なる組の数に差がなかった為。設定と、重なる組の数のデバッグ表示も消す
18. 敵の状態の配列の長さは有効なスポーン位置の編成の人数の合計、グループの配列の長さは有効なスポーン位置の数にする。同時に存在する数の上限の設定はなくす
19. 追跡範囲の外（距離マップを計算していない所）では、部隊は記録した帰りの道筋を逆にたどる移動だけを行う。待機中の部隊は移動の処理を止め、待機の姿勢で描くだけにする（2026-10-10）
20. 帰還中の部隊は、追跡範囲の外へ出ても帰りの道筋をたどって持ち場まで歩く。範囲の外へ出たときに持ち場へ移す（テレポートさせる）ことはしない。道を壊して部隊を分断しておく遊び（決めたことの 11）が成り立たなくなる為

### 部隊の意思決定

13. 部隊ごとに意思決定する方式にする（2026-10-10）。比べた方式は次の 3 つ
    - 固定ルートの巡回：ルートを封鎖・追加して地形の変化に合わせられるが、同じ場所で戦い続けると敵が増える
    - プレイヤーを基準にした目的地（区間4D の方式）：軽いが、プレイヤーから決まった相対位置に並ぶので単調に見えやすい
    - 部隊ごとの意思決定：部隊の数だけ処理が増えるが、部隊単位で目的地・陣形・行動を精密に決められ、遊びを調整しやすい
14. 部隊ごとの意思決定を選んだ理由
    - 部隊の数は数十程度なので、部隊ごとに判断しても重くない
    - 敵の行動の処理が EngineAdapter の Job の中にしかない状態を解消できる
    - Application が部隊の位置と状態を知っているので、攻撃するか、バリアを張るか、陣形を変えるか、といった制御を足せる
    - 固定ルートの巡回とプレイヤーを基準にした目的地は、Application が選ぶ行動の 1 つとして作れる
15. 役割の分け方
    - Application：部隊の状態（待機・追跡・帰還・撤退など）、目的地、陣形を決め、State で公開する
    - EngineAdapter：State を読み、経路探索（距離マップ）、アンカーの移動、隊列の制御、個々の敵の移動を Burst の Job で行う。部隊の観測（アンカーの位置、残りの人数、着いたか、進めないか）を返す
16. 撤退・補充・全滅後の出し直しは、Application の部隊の意思決定の中に作る

## 検討中の提案（2026-10-10、ユーザー）

- 範囲の外の敵の見た目：VAT（アニメーションのテクスチャ）に焼いたアニメーションで見た目だけ動かし、近くに来たら脚の IK の体に置き換える。敵はパーツごとの硬いメッシュなので、頂点ではなくパーツの位置と回転を焼く方法もある。置き換えの境目で、焼いた歩き方と IK の足の位置をどう合わせるかを決める必要がある
- 範囲の外の巡回：待機中の部隊を止めるのではなく、決まったルートを巡回させる。VAT で範囲の外の敵を動かして見せるなら、巡回させても違和感がない。ルートの持たせ方（スポーン位置ごとか）、巡回中に範囲へ入ったときの追跡の始め方、帰還の行き先（持ち場か巡回のルートか）を決める必要がある
